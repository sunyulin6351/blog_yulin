最近在 Hacker News 上看到一个很有意思的问题：

> 对于一个普通人来说，如果希望通过学习 LLM、AI Agent 以及相关技术，从 AI 浪潮中获得实际收益，究竟应该掌握哪些具体技能？

提问者希望得到的不是泛泛而谈的趋势判断，而是可以通过互联网和个人实践独立学习的具体技能。

这个问题引起了不少讨论。有人建议学习模型训练，有人推荐构建 Agent，有人强调工程思维、测试验证，也有人认为最重要的其实是沟通能力和管理能力。

这些回答看起来各不相同，但仔细梳理之后，我发现它们指向了一个共同的方向：

**AI 正在降低知识和执行的门槛，但真正稀缺的能力，正在转向如何定义问题、组织 AI、验证结果，以及将这些能力沉淀为可以重复运行的系统。**

这可能比学习某个具体的 AI 工具更值得关注。

## 一、不要只想着学习 AI，而要学习如何利用 AI 创造价值

讨论中有一个观点让我印象很深。

一位参与者认为，互联网兴起的时候，如果一个人希望从互联网的发展中获得商业收益，他当然可以去研究路由器、网络协议和通信技术，但真正创造巨大商业价值的，并不只有这些底层技术公司。

Google 和 Amazon 等公司做的事情，是利用互联网解决人们和企业真正需要解决的问题。

这个类比放在今天同样成立。

现在有很多人在学习 AI，关注模型参数、上下文窗口、推理能力、Prompt 技巧，以及各种 Agent 框架。这些知识当然有价值，但它们并不直接等于创造价值的能力。

真正值得思考的问题是：

- 能不能利用 AI 完成过去需要多人协作才能完成的工作？
- 能不能把原本依赖个人经验的工作流程自动化？
- 能不能构建一个持续运行的服务，而不是每次都从头向 AI 提出要求？
- 能不能利用 AI 发现新的需求，并将其转化为产品或服务？

从这个角度看，学习 AI 的目标不应该仅仅是成为一个更熟练的 AI 使用者，而应该是成为一个能够利用 AI 构建和运营系统的人。

**技术本身是手段，能够解决什么问题、创造什么价值，才是最终目的。**

## 二、比 Prompt Engineering 更重要的是工程思维

原帖中有一条评论，我认为非常值得反复琢磨：

> Learn how to think like an engineer.

这位评论者观察到，他接触过很多没有工程背景、但希望利用 AI 解决业务问题的人。他发现，这些人在使用 AI 自动化工作时遇到的困难，往往不是模型能力不足，而是缺少工程化思维。

他总结了几个基本能力：

1. 能够把一个复杂问题拆解为具体流程和步骤。
2. 能够准确描述真正需要解决的问题，而不是只描述自己想到的解决方案。
3. 能够明确怎样判断问题已经解决。
4. 能够追问 AI 是如何完成任务的，从而理解过程并发现改进空间。
5. 能够识别 AI 是否陷入错误方向，并及时纠正。
6. 能够理解 LLM 擅长什么、不擅长什么。

我觉得这实际上揭示了 AI 使用能力的一个重要分水岭。

举个例子。

假设我们希望 AI 帮助完成一份行业研究报告。

一种做法是直接告诉 AI：

> 帮我研究一下某个行业，生成一份完整的研究报告。

这种方式看起来简单，但最终结果可能存在资料来源不可靠、分析逻辑不完整、数据口径不一致等问题。

另一种做法，是先把任务拆解清楚：

- 明确研究目标和受众。
- 确定需要回答的核心问题。
- 划分资料收集、信息核验、数据分析和报告编写等环节。
- 明确每个环节需要什么输入、产生什么输出。
- 规定资料来源和引用要求。
- 设置最终报告的质量检查标准。

这样，AI 才有可能在一个相对明确的框架内完成工作。

两种做法的区别，并不在于 Prompt 写得长还是短，而在于使用者是否真正理解了任务本身。

过去，我们需要自己掌握很多执行细节，才能完成一项复杂工作。

现在，AI 可以承担越来越多的执行工作，但我们仍然需要知道任务应该如何拆解、结果应该是什么样子，以及怎样判断它做得对不对。

**AI 降低了执行门槛，却没有消除工程思维的重要性。**

## 三、从使用 AI 到管理 Agent：人和 AI 的协作方式正在发生变化

另一个很有意思的讨论，是把 AI Agent 的使用比作管理一个团队成员。

这并不是说 AI 和人具有相同的能力，而是两者在任务协作上有一些相似之处。

当我们刚开始使用一个 Agent 时，往往需要非常明确地告诉它应该做什么、按照什么步骤执行，以及哪些事情不能做。

随着对模型能力的理解不断加深，我们可以逐渐提高任务的抽象层级。

例如：

**第一阶段：明确指令。**

告诉 AI 具体应该执行哪些步骤，使用什么工具，最终输出什么结果。

**第二阶段：目标导向。**

告诉 AI 希望实现什么目标，让它自己决定执行路径，但仍然保留必要的检查点。

**第三阶段：任务委派。**

把完整任务交给 Agent，由它自行拆解任务、调用工具、处理问题，并在关键节点向人反馈。

**第四阶段：系统协作。**

多个 Agent 分别承担研究、分析、执行和验证等职责，通过统一的工作流协同完成复杂任务。

这里有一个重要变化：

我们不再需要事无巨细地告诉 AI 应该怎么做，而是逐渐转向定义目标、约束条件和验收标准。

当然，这并不意味着任务描述越抽象越好。模型始终存在能力边界，任务抽象层级必须与模型的实际能力相匹配。

真正重要的是，随着模型能力提升，我们也要不断调整自己与 AI 的协作方式。

这实际上是一种新的管理能力：知道什么时候应该指导，什么时候应该放权，什么时候需要介入纠偏。

## 四、真正值得研究的是 Agent Harness，而不只是 Agent

讨论中还有一位参与者给出了三个值得学习的技术方向：

1. 自己训练一个模型。
2. 为模型构建 Harness。
3. 在模型和 Harness 之上构建 Agent 与 Orchestrator。

其中，我认为第二和第三项尤其值得关注。

先解释一下这几个概念。

**模型（Model）**

负责理解输入、生成内容、推理和决策，是整个系统的智能核心。

**Harness**

可以理解为围绕模型构建的一整套运行和控制环境。

它不仅包括 Prompt，还包括上下文管理、工具调用、执行循环、状态管理、错误处理、权限控制等机制。

**Agent**

将模型与工具、任务目标和执行机制结合起来，使模型能够自主推进任务。

**Orchestrator**

负责协调多个 Agent 或任务模块，管理它们之间的执行顺序、依赖关系和结果交接。

为什么我认为 Harness 特别重要？

因为一个模型本身并不等于一个能够完成工作的系统。

例如，让模型分析一份文件，它可能可以直接给出分析结果。

但如果希望它长期、稳定地承担这类工作，就需要进一步解决很多问题：

- 文件从哪里获取？
- 如何判断文件是否完整？
- 如何管理上下文，避免信息丢失？
- 如果模型调用工具失败，是否能够自动重试？
- 如果任务执行到一半中断，能不能恢复？
- 如何记录执行过程？
- 如何判断最终结果是否符合要求？
- 哪些操作必须经过人的确认？

这些问题都不是单纯提高模型能力就能解决的。

它们需要通过模型之外的工程机制来完成。

这也是为什么我认为，未来真正有价值的 AI 应用能力，很可能不是简单地掌握某个 Agent 产品，而是理解 Agent 背后的运行机制，知道如何构建、调整和控制它。

**模型决定系统能够达到什么样的智能水平，Harness 和 Orchestrator 则在很大程度上决定这种智能能否转化为稳定、可控的实际工作能力。**

## 五、AI 越会生成，验证能力就越重要

原帖中还有一个非常务实的观点：

随着 AI 生成代码和内容的能力不断增强，真正的瓶颈可能正在从生产转向验证。

尤其是在软件开发领域。

过去，开发人员需要花费大量时间编写代码。现在，AI 可以快速生成大量代码，但这些代码是否正确、是否满足需求、是否引入新的问题，仍然需要验证。

因此，有参与者建议重点学习：

- 测试驱动开发（TDD）
- 单元测试（Unit Testing）
- 集成测试（Integration Testing）
- 端到端测试（End-to-End Testing）
- Playwright 等自动化测试工具
- pytest 等测试框架

这背后有一个值得注意的变化：

当生产成本下降时，质量控制的重要性反而会提高。

这并不只适用于软件开发。

AI 生成一份报告，如何核验事实和数据？

AI 制作一份 PPT，如何检查内容逻辑、页面结构和视觉质量？

AI 自动操作浏览器，如何确认它完成了正确的操作？

AI 执行一项业务流程，如何避免因为某个步骤失败而产生错误结果？

这些问题都指向同一个方向：不能只关注 AI 是否完成了任务，还要建立一套能够判断任务是否正确完成的机制。

我认为未来的 AI 系统至少应该具备几个基本能力：

1. **可验证：** 能够检查输出是否符合预期。
2. **可追踪：** 能够记录关键操作和执行过程。
3. **可恢复：** 发生错误后能够重试或从中断处继续。
4. **可控制：** 对高风险操作设置权限边界和人工确认。
5. **可评估：** 能够通过测试和指标持续衡量执行质量。

如果一个 Agent 只能在演示时成功，却无法稳定地完成日常任务，那么它还不能算是真正可靠的生产力工具。

## 六、不要忽视传统计算机基础

讨论中还有不少人建议学习一些看起来并不那么时髦的技术：

- Python
- Linux 和 Bash
- API
- 数据库
- 网络基础
- Git
- 信息安全
- 系统设计

为什么这些基础知识在 AI 时代依然重要？

因为 Agent 正在从一个只负责生成文本的聊天工具，逐渐变成一个能够操作真实系统的软件执行主体。

它需要读取文件、访问数据库、调用接口、操作浏览器、运行程序，甚至管理本地环境。

如果我们完全不了解这些基础设施，就很难判断 Agent 为什么执行失败，也很难为它提供正确的工具和运行环境。

当然，这不意味着每个人都需要成为专业软件工程师。

我更倾向于一种实用的学习方式：围绕自己希望 AI 完成的任务，反向学习所需要的技术。

例如：

希望 AI 能够自动处理文件，就学习 Python 文件操作和相关库。

希望 AI 能够访问业务系统，就学习 API 和数据库。

希望 AI 能够在本地运行任务，就学习 Linux、Shell 和进程管理。

希望 AI 能够稳定运行，就进一步学习日志、异常处理、测试和权限控制。

这样学到的知识能够立即用于实际任务，也更容易形成长期积累。

## 七、真正的竞争优势，仍然来自人的判断力和领域经验

讨论中还有一个观点值得特别注意：

AI 可以帮助我们完成很多技术工作，但它并不意味着每个人都能创造出同样有价值的东西。

一位参与者认为，AI 的使用门槛正在降低，但人类的经验、审美、判断力，以及对真实问题的理解，仍然具有重要价值。

我很认同这一点。

假设两个人都能使用同样的 AI 模型。

一个人不了解某个行业，只能让 AI 根据公开资料生成内容。

另一个人长期在这个行业工作，知道客户真正关心什么，知道哪些问题是表面现象，哪些问题才是业务的核心，也知道什么样的结果才有实际价值。

即使使用相同的模型，两个人最终得到的成果也可能有很大差异。

这说明，AI 并没有让领域知识失去价值。

相反，当 AI 承担越来越多执行工作时，能够识别真正有价值的问题、判断结果质量的人，可能会获得更大的杠杆效应。

还有一个容易被忽视的问题：如果把思考和学习也完全外包给 AI，我们可能会逐渐失去独立判断的能力。

AI 可以作为老师，帮助我们理解原本不熟悉的知识；也可以作为助手，帮助我们探索新的技术领域。

但我们仍然需要主动理解、实践和验证。

否则，虽然工作速度提高了，却不一定真正积累了自己的能力。

## 八、普通人应该如何开始？

如果把上面的讨论转化为一条可以实际执行的学习路线，我认为没有必要一开始就去研究复杂的模型训练，也不需要追逐所有新出现的 AI 工具。

更合理的方式，是从自己熟悉的工作入手，逐渐建立完整的工程能力。

### 第一步：把 AI 当作真正的工作伙伴

不要只用 AI 搜索资料、回答问题，而是尝试让它承担完整任务。

例如：

- 自动整理和分析一批资料。
- 根据已有材料生成结构化报告。
- 自动处理重复性的文件操作。
- 帮助排查和解决实际技术问题。
- 完成一项需要多个步骤的研究任务。

关键是亲自观察 AI 在哪些地方能够独立完成工作，哪些地方容易出错。

### 第二步：学习 Python 和 API

不需要一开始就学习复杂的数据结构和算法。

先掌握能够解决实际问题的基础能力：

- Python 基础语法。
- 文件读写和数据处理。
- HTTP 请求和 API 调用。
- JSON 数据结构。
- 数据库基本操作。
- Linux 和 Shell 基础。

目标不是成为一名专业程序员，而是具备独立构建简单工具、理解 AI 生成代码和排查基本问题的能力。

### 第三步：尝试自己构建一个 Agent

从一个具体任务开始，逐渐理解 Agent 的工作机制。

例如，构建一个能够自动完成资料收集、内容分析、结果整理和报告生成的 Agent。

在这个过程中，重点学习：

- 模型调用。
- 上下文管理。
- 工具调用。
- 任务拆解。
- 执行状态管理。
- 错误处理。
- 人工介入机制。

不要满足于调用现成的 Agent 产品，而要尝试理解它背后的运行逻辑。

### 第四步：让 Agent 从能够运行变成可靠运行

为前面构建的 Agent 增加必要的工程机制。

例如：

- 记录执行日志。
- 设置任务超时和重试机制。
- 对输出结果进行自动检查。
- 为关键步骤增加人工确认。
- 对任务失败进行告警。
- 支持任务中断后的恢复。

这一步可能没有前面那么有趣，但它决定了一个 Agent 能否真正承担长期工作。

### 第五步：将单个 Agent 扩展为一套工作系统

当一个 Agent 能够稳定完成某项任务后，再考虑将多个任务连接起来。

例如：

一个研究 Agent 负责资料收集，一个分析 Agent 负责提炼观点，一个写作 Agent 负责形成初稿，一个审核 Agent 负责检查事实和逻辑。

通过任务编排，让它们形成一个完整的工作流程。

最终，人不再需要参与每一个执行步骤，而是负责确定目标、提供必要的背景信息、处理异常和审核关键结果。

这才是我理解的 AI 自动化真正有价值的方向。

## 九、从 AI 使用者，走向 AI 系统的设计者

回到 Hacker News 上的那个问题：普通人究竟应该学习哪些 AI 技能？

我认为，可以把这些能力归纳为五个方面：

| 能力 | 核心内容 |
| --- | --- |
| 问题定义 | 识别真实需求，拆解复杂任务 |
| AI 协作 | 掌握模型使用、Agent 管理和任务委派 |
| 工程实现 | Python、API、数据库、Linux、系统设计 |
| 质量控制 | 测试、评估、日志、异常处理和权限管理 |
| 领域判断 | 业务理解、经验积累、沟通和决策 |

它们并不是相互独立的技能，而是一个完整的能力体系。

我越来越觉得，AI 时代真正值得投入时间的，不是不断学习新的工具、收集新的 Prompt，或者追逐每一个新出现的 Agent 框架。

而是选择一个真实的问题，利用 AI 尝试解决它，然后不断补齐过程中暴露出来的知识和能力缺口。

当你能够独立设计一套工作流程，知道如何让 AI 执行任务，知道怎样验证它的结果，也知道如何处理异常和持续改进时，你就不再只是一个 AI 工具的使用者。

你已经开始具备构建 AI 工作系统的能力。

**未来人与 AI 的竞争优势，可能不再主要取决于谁掌握了更多知识、写出了更多代码，而是谁更善于定义问题、组织智能、控制执行，并将这些能力沉淀为可持续运行的系统。**

这或许才是 AI 时代最值得学习的一项技能。
